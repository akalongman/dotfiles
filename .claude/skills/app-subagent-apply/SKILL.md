# Implementing through subagents

**REQUIRED SUB-SKILL:** superpowers:subagent-driven-development defines the loop (dispatch, task review, fix rounds, ledger, final review), tested against superpowers 6.4.1; invoke it once at launch for the pre-flight scan and its scripts. This session is the driver and never runs the loop itself: each unit runs inside one `app-sdd-unit-controller` subagent (definition in `~/.claude/agents/`, the loop preloaded), which dispatches the implementer and reviewers one layer down under `prompts/unit-controller-overrides.md`, passed by path. This skill adds the source adapter, this machine's constraints, the driver loop and the hands-off ending.

**Input:** `$ARGUMENTS` is an OpenSpec change name, a plan file path, a PRD or spec path, or empty (infer from the conversation; several candidates: AskUserQuestion), optionally followed by `step` or `hands-off`, `isolated`, and `tier=<alias>`. Announce "Using source: <name>" and the options given.

## Sources

| Source | Detect | Unit, brief, mark |
|---|---|---|
| OpenSpec change | `openspec/changes/<name>/tasks.md` exists | one `## N.` section (`2b` is its own); `scripts/openspec-section-brief <name> <N> <ws>/section-N-brief.md`; completion marked only by `scripts/openspec-section-tick <name> <N> '<ledger line>' [ids]`, which validates the ids, then writes the ticks and the ledger line together (exit 5: an id is not in the section, nothing written) |
| Superpowers plan | a `Task N` heading at level 2 or deeper | one task per the sub-skill; `scripts/task-brief <plan> <N> <ws>/task-N-brief.md` (this copy keeps trailing sections and `Task Nb` out of the brief) |
| PRD, spec, issue | anything else | superpowers:writing-plans first, then continue as a plan |

`<ws>` is `.superpowers/sdd/<name>/` for OpenSpec (every change's file is `tasks.md`, so never run `sdd-workspace`; give every sub-skill script this OUTFILE) and the sub-skill's default for plans. Ledger lines say `Section N:` or `Task N:`. Dispatch prompts carry paths only; design, spec and prior-unit context never travel inline.

**OpenSpec.** Load with `openspec instructions apply --change <name> --json | jq '{state, progress, tasks, instruction}'`, never raw. `blocked`: print the instruction, stop. `all_done`: with a `Final phase: complete <sha7>` ledger line at the current HEAD, first release a held final phase and run the steps its hold deferred (This machine, item 1), then render the table, suggest `/opsx:archive`, stop; without one the units are ticked but the final phase is owed (an interrupted run), so go to the final phase below. `ready`: read `tasks.md` and the spec deltas once for the pre-flight scan; proposal and design reach implementers as paths. "Mark complete as you go" is superseded: the unit controller ticks after review. Command-only items run in the driver; prose-only edits are the driver's, covered by the final review; anything executable or declarative goes to a unit; an external side effect stops for the user unless hands-off. A task that can only run after merge is a source defect: the pre-flight scan flags it and it is amended with the user into a pre-merge task that writes it to the merge request's `### Post-merge checks` list, never parked, because the change archives before the request merges. A mismatch between code and source returns as `needs-ruling`: amend the source with the user, `openspec validate <name> --strict`, regenerate the brief, resume the controller. At the end, render what `instruction` asks, suggest `/opsx:archive`, delete `<ws>` only after the archive.

## This machine

1. **Resume.** If `<ws>/progress.md` exists: `head -n 3`, `grep -nE '^(Run base|Commit mode|Model policy|Model fallback|Gates|Ruling|Ruling \(controller\)|Open before merge|Hands-off|Final phase):|: (complete|parked|blocked|paused|pause requested|pause released|resumed|handed to controller)|stopped by hand'`, `tail -n 20`; never the whole file. Keep its units, rulings and answers; re-dispatch nothing marked complete or parked. A unit with a `handed to controller` line and no `complete`, `parked` or `blocked` line is an incomplete attempt, and so is the final phase once `<ws>/final-brief.md` exists and no `Final phase: complete` line is written, its paths being every unit's: re-dispatch it with the prior-attempt framing of the driver loop's item 3. The relaunch counts as the owner's `continue`: a request still in force (as the driver loop's item 4 defines it) is released with a `Section N: pause released` line (`Final phase:` for the final phase) before the first dispatch. A relaunch whose ledger shows the final phase held (`Paused by user after the final phase` with no `Final phase: pause released` after it) writes that release and then runs the steps the hold deferred (the driver loop's item 3), for a plan and for an OpenSpec change alike; for OpenSpec this comes before the `all_done` branch's table.
2. **Branch.** The run commits on the current branch, path-limited per `~/.claude/rules/git.md`, the default branch included; never create or switch a branch unless `isolated` was given. Stop on uncommitted changes in the units' files, except the paths of an incomplete attempt (item 1); those edits travel with the hand-over. Ledger `Run base: <sha7>` and `Commit mode: commit on <branch>`.
   **Isolated.** With `isolated`: find the project's bootstrap, the first that exists: `composer worktree:setup`, `npm run worktree:setup`, `make worktree:setup`; none: stop before any worktree, branch or dispatch and say so. Then `git worktree add .worktrees/<name> -b <name>` from HEAD and run the bootstrap. Run from the worktree; ledger `Commit mode: commit on <name> in .worktrees/<name>`. The worktree stays until the user runs the project's teardown.
3. **Models.** Aliases `sonnet`, `opus`, `fable`. Unit controllers, implementers and reviewers dispatch on `opus`, or on `tier=<alias>` when given; the final review and fix rounds 4 and 5 on `fable`, which is capped on this account; `sonnet` only for a unit the user names. Ledger `Model policy: <tier per role>` before the first dispatch. On `rate_limit`, `429` or `reached your <tier> limit`: ledger `Model fallback: <role> <from> -> <to>`, run that role one tier down for the rest of the run, never re-probe; a unit controller that hits it writes the same line, and every later dispatch reads the marker lines first.
4. **Gates.** superpowers:verification-before-completion with the project's own lint, analysis and test commands (OpenSpec: `openspec validate <name> --strict` first, and in the final phase the project's `specs:lint` script when it has one); none defined: say so. The unit controller runs them per unit and in the final phase; ledger `Gates: <commands> passed`.

## Driver loop

Pre-flight once: if this session already holds a drafting conversation about the source, say that the run will re-read it on every driver turn and that a fresh session avoids it, then continue; read the installed sub-skill's version directory under the plugin cache, ledger `Sub-skill: <version>`, print one warning line if it is not 6.4.1; then the sub-skill's scan of the whole source, rulings into `<ws>/decisions.md`, and for every unit the earlier units it needs (an interface, a migration, a file they create) as `Section N depends on: <units or none>` lines there. Then for each unit in order:

1. If a unit it depends on is parked, ledger `Section N: blocked by parked Section M` and take the next unit; nothing is dispatched. Otherwise write the brief with the source's script. Ledger `Section N: handed to controller`.
2. Dispatch `app-sdd-unit-controller` on the tier of item 3 with paths only: the brief, `<ws>/section-N-report.md`, `<ws>/section-N-review.md`, `<ws>/progress.md`, `<ws>/decisions.md`, this skill's `prompts/unit-controller-overrides.md`, the source's tick command, and the line `Mode: hands-off` when given. Then end the turn: its hand-back re-invokes you; never poll for it.
3. Before the cases below: a return or notification from any controller other than the unit's live attempt (the live attempt is the controller id of your latest dispatch for this unit; an attempt is over once its own return was ledgered `failed` or `parked` or the unit's `complete` line is written), from an agent of a superseded attempt (a child of a controller already replaced), or a stop notification for one of the stops the driver issued itself (either cleanup, this item's stop-notification rule, `abort`) is ledgered `Section N: late return from superseded attempt, consumed` and acted on no further; what was already due for that unit (the `failed` path's re-dispatch, a hold) goes on as it stood. `complete` or `parked`: next unit, except that while a request is in force (item 4) it is held like any other return (below) and the next unit waits for `continue` (in the final phase, `scripts/run-archive`, the final message and the hands-off push and request wait in its place, and on `continue` the driver ledgers `Final phase: pause released` and then runs them in the usual order); with `step`, first show the block and ask continue or stop (AskUserQuestion), and on stop ledger `Stopped by user after <unit>` and end. Every return that is not `complete` and not consumed above is ledgered as `Section N: controller returned <status>` before acting on it, so a resumed driver can count attempts. `needs-ruling`: ask the user (AskUserQuestion), ledger `Ruling: <answer>`, append it to `decisions.md`, resume the same controller by message with the ruling; under hands-off it is a controller defect: resume it once with "Mode: hands-off: rule and continue", and a second one parks the unit. `paused`: ledger `Section N: controller returned paused (<point>)`, print the point and end the turn; on `continue`, first ledger `Section N: pause released` when a request is in force (item 4), then resume the same controller by message ("Resume from your paused point"); the controller ledgers its own `resumed`. A `needs-ruling` it returns on that resume is asked of the owner under hands-off too, never sent down the defect path, and a "stop" answer to the drift question is `abort`. `waiting` (the harness forced the controller to hand back while its child was in flight): ledger `Section N: controller returned waiting (child <id>)`, end the turn and ask nothing; the child's own hand-back then reaches the driver, because its parent's run ended. An interim notification for that child (it waits on its own background work) is a wait. On the child's hand-back, or a `killed` or `failed` notification for that child, resume the same controller by message with the child's status, commits and report path, or the notification itself, ledger `Section N: relayed <role> hand-back to controller` (`notification` in place of `hand-back` for a notification) and end the turn, hands-off included, without asking. A `waiting` return and its relay are never held, and nothing is forwarded to the waiting controller, since a message would wake it; a pause reaches it through the ledger after the relay. A `waiting` return whose child never reports is a wait, not a failure; `abort` still applies. Any other return while a request is in force (item 4) is held: ledger it as this item says, then `Paused by user after <unit>`, and act on it only on `continue`; the hold defers the next dispatch only (in the final phase with no dispatch left, `scripts/run-archive`, the final message and the hands-off push and request in its place), and the `failed` and background-work cleanup runs at once. Prose with no block: resume the same controller by message asking for its return block; a second prose return counts as `failed`. A result saying the controller has not reported yet is a wait, not a resume. A hand-back whose notification says the controller stopped with background work still running: ledger `Section N: controller left background work`, stop the controller by its id (TaskStop) before the next dispatch, and accept the block as it stands. `failed`, or an error on the dispatch: first run ListAgents and TaskStop every agent from the failed attempt that is still running or stopped with background work, because a controller's hand-back does not prove its implementer has stopped (2026-10-13, an orphaned implementer ran beside the retry on the shared tree); then dispatch once more with "A prior controller attempted this unit; read the ledger tail, the report and `git diff --stat` on the unit's paths first"; a second failure stops the run, or under hands-off ledgers `Section N: parked (controller failed twice)` and moves on. A controller whose result is a stop notification with status killed and no result (`<status>killed</status>`, no `<result>`), for a stop the driver did not issue, was stopped by the owner: ledger `Stopped by user mid-unit <N>`, ListAgents and TaskStop every child of that attempt (the `failed` cleanup without its re-dispatch), dispatch nothing until `continue`, then dispatch once with the prior-attempt framing; the driver's own stops and a superseded attempt never reach this rule, since the head of this item consumes them.
4. Never edit source, the task file or a unit's ledger lines yourself. The owner's words `pause`, `continue` and `abort` act on the run. On `pause`: ledger `Section N: pause requested` (N the live unit, or with none live the next one; for the final phase, live or next, this item's lines take `Final phase:` in place of `Section N:`, and `Stopped by user mid-unit <N>` and `Paused by user after <unit>` name it as `the final phase`), say "pause requested; the unit pauses when its current implementer or reviewer reports" (with none live, "pause requested; nothing is dispatched until `continue`") and end the turn; forward nothing. On every `continue`, `abort`'s included: first, when a request is in force (of the unit's `pause requested` and `pause released` lines, the latest is `pause requested`), ledger `Section N: pause released`; then resume a controller that returned `paused` by message (item 3), act on a held return, give a stopped unit item 3's fresh dispatch, or make the dispatch, or ask again the question, that the pause deferred; a unit still running or waiting needs nothing more when this `continue` released its request, the release being the cancel; otherwise say there is nothing to resume. A bare `stop` mid-unit is read as `pause`, and you say so; any other request in words to stop an agent or the unit goes through `abort`; while `step`'s continue-or-stop prompt is open, its answer wins. On `abort`, the emergency route: TaskStop the controller first (a handed-back one answers that it is not running), then ListAgents and TaskStop every child of the attempt anyway, ledger `Stopped by user mid-unit <N>` and wait for `continue`, which resumes a controller that returned `paused` (one woken by its child's stop does) and gives any other the fresh dispatch. When a child's stop succeeded under a controller that answered not running, that controller's `paused` return is due: on a `continue` before it arrives, run ListAgents, and while it shows that controller running, answer "the controller's paused return is still due" and dispatch nothing; otherwise `continue` gives the fresh dispatch, as for a controller that was itself killed or whose children were all already stopped, and the late `paused` return, now from a superseded attempt, is consumed. Never stop a child as the way to pause (the 2026-10-18 incident): a controller woken by a child stopped by hand returns `paused` and is held. Any other message from the owner during a unit is never forwarded: a question you answer from the workspace files (the report, the review, the ledger, `git diff`); an instruction for the unit you ledger as `Section N: owner note: <text>` (with none live, for the next unit), which its controller reads before every dispatch and before the tick and applies at the note's first carry to an implementer. Nothing else reaches a controller by message but a resume and a ruling.

After the last unit, write `<ws>/final-brief.md` (Run base, HEAD, the gate commands, and the ledger's deferred, parked, blocked and ruling lines as a path), dispatch `app-sdd-unit-controller` for the final phase with the same paths plus `<ws>/final-review.md`, and wait. Its return goes through item 3 like any unit's, with `Final phase:` as its ledger prefix: `complete` means the gates passed and the controller ledgered `Final phase: complete <sha7>` at the reviewed HEAD; anything else, after item 3's resumes and second attempt, ends the run with `Final phase: <status>` ledgered and no `/opsx:archive` suggestion. Either way, once item 3 has acted on the return (a held return only on `continue`, after the `Final phase: pause released` line), run `scripts/run-archive <ws>`: it copies the workspace and the run's facts (transcript path, repository, branch, skill hashes, sub-skill version) to `<config dir>/docs/tmp/apply-runs/` and prints the path. The final message states the final phase's status, lists every `Ruling:`, `Ruling (controller):`, blocked and `Open before merge:` line and ends with that path. Skip finishing-a-development-branch; beyond the run's own commits, the driver commits or pushes nothing unless asked or under hands-off.

## Hands-off

With `hands-off` nothing stops after the launch: unit controllers rule on their own reading and ledger `Ruling: <decision>. Cost if wrong: <what>`; mismatches are parked. After a final phase that returned `complete`, once the driver loop's item 3 has acted on the return (a held return only on `continue`, after the `Final phase: pause released` line): `git push -u <remote> <branch>`, the remote being the branch's own or `origin` when it has none. Off the default branch, open the request with the run summary and every `Ruling:`, `Ruling (controller):`, parked and `Open before merge:` line as its description: `glab mr create` when the remote's fetch URL host is a GitLab instance (self-hosted included), `gh pr create` when it is `github.com`, otherwise stop and say the branch is pushed. On the default branch, push and open nothing. Ledger `Hands-off: pushed <sha7>, <request URL or none>`. Any other final status: ledger `Hands-off: not pushed (<status>)` and stop; the work stays local.
